# Audit signals: what each one checks, and how to triage it

Detail layer for `audit-carla-docs`. Each signal is independent; a finding is a
*candidate*, not a verdict.

## 1. changelog

Lists every feature in the `## LATEST Changes` section as an unticked checkbox.
**It does not check whether anything is documented** — you do that by hand.

Each `* ` entry is classified by its leading verb:

| verb | treated as |
|---|---|
| Added, Changed, Renamed, Optimized, Removed, Deprecated, Exposed, Replaced, Reworked, Moved, Updated, Ported, Documented | feature — listed |
| Fixed, Reverted, Corrected, Restored | repair of existing behaviour — skipped |
| anything else | listed, marked *verb not recognised — check* |

Entries are cut at the first sentence end, capped at 220 characters. The cut is
on a full stop followed by a capital or a backtick, never on a colon: CARLA's
entries routinely read "Reworked the RGB camera look: <the actual content>", and
cutting at the colon threw the content away.

### Why there is no automatic coverage check

An earlier version substring-matched each entry's backticked names against all
of `Docs/`. It was abandoned as too generous to trust:

- a bare mention anywhere counted as documentation, with no check that anything
  was explained;
- one matching name cleared an entry naming six new functions;
- a page describing the *old* behaviour still matched, so changed features
  looked documented;
- `python_api.md` is huge and generated, so it absorbed names and quietly
  cleared them.

It under-reported, which is the worst failure mode for an audit — an invisible
gap. Listing everything and making a human tick it off is honest about what the
tool knows. Automating it again is possible, but it needs a notion of "explained
in the right place", not "name appears somewhere".

## 2. binding

Parses `class_<...>("Name")` out of `PythonAPI/carla/src/*.cpp` and checks for a
matching `class_name: Name` in `PythonAPI/docs/*.yml`.

**Fix these in the `.yml`, never in `Docs/python_api.md`.** That page is
generated by `PythonAPI/docs/doc_gen.py`; an edit to the `.md` is reverted the
next time anyone regenerates, silently. After editing the yml:

```bash
cd PythonAPI/docs && python3 doc_gen.py
```

Members are checked too. Each `class_<>()` registration owns the source up to
the next one, which is what ties a `.def`, `.add_property`, `.def_readwrite` or
`.def_readonly` to the class that exposes it; a finding is then either a whole
undocumented class (`RssSensor`) or one member missing from a documented class
(`Actor.apply_texture`). Dunders are exempt, as in `stale` — the ymls document
them in bulk, not per class.

This was classes-only at first, on the assumption that member-level checking
would drown in operators and trivial accessors. It does not: the member
findings are real API, and they are what the `python-api` writing category
consumes.

Every finding is one line, since the section heading already says what it is.
That holds across the report: `sensor` and `catalogue` drop the detail that
restated their heading, and `catalogue` groups by its source file so the long
`Content/Carla/Config/...json` path is on the heading rather than on every
line. A note in brackets survives only when it adds something, like
`(only in adv_recorder.md)` for an actor that is mentioned somewhere other
than its catalogue page.
Both Python sections are grouped under a `###` heading per owning class, with
the source file on the heading, because the work is per class: one heading is
one yml block to edit. Whole-class findings come first, in their own group.
Each line ends with what it is: `(new class)`, `(new function)` or `(new attribute)`. The kind
comes from the registration call — `.def` is a function, `.add_property`,
`.def_readwrite`, `.def_readonly`, `.add_static_property` and `.value` are
attributes — never from the name, which says nothing: `bone_transform` is a
class, not a function.

An undocumented class is skipped when it **adds nothing of its own**: no
member the registration names, or none that an ancestor does not already
document. There is no page to write for such a class, so the finding could
never be closed. This covers three shapes with one test:

- `class_<std::vector<...>>` container registrations, whose only members come
  from `vector_indexing_suite` and are never named
- hierarchy nodes like `ClientSideSensor` and `LaneInvasionSensor`, registered
  so `bases<>` resolves and `spawn_actor` can return a concrete type
- `ServerSideSensor`, whose seven methods are documented on `carla.Sensor`,
  since the ymls flatten the sensor hierarchy

`bases<>` is read off the registration and followed transitively, so a class is
measured against everything it inherits. Members whose names the registration
never spells -- `init<>`, `self_ns::str`, an indexing suite -- do not count as
its own.

If a container ever shows up as a **return type** in Python, that is a missing
`CALL_RETURNING_LIST` in the binding, not a documentation gap.

`enum_<>` registers a Python class exactly as `class_<>` does, so both are
matched. Missing that cost twelve findings, among them the `RssLogLevel` and
`RssRoadBoundariesMode` enums and the `CityObjectLabel` values that replaced
the documented `Vehicles` (`Car`, `Bus`, `Truck`, `Motorcycle`, `Bicycle`,
`Rider`, `Train`).

**Quoting.** The ymls write `var_name: 'y'`, because a bare `y` is a YAML 1.1
boolean. A name pattern that does not allow the quotes reports `Vector2D.y`,
`Location.y` and friends as undocumented.

## 3. sensor

Sensor ids are rarely written out. They are built inside the `Make*Definition`
helpers by `FillIdAndTags(Def, TEXT("sensor"), TEXT("<group>"), <name>)`, where
`<name>` is usually a parameter supplied at the call site. The audit therefore:

1. resolves each helper to its group from its own `FillIdAndTags` line;
2. takes the literal name from each **call site** of a parameterised helper,
   applying any `+ TEXT("_suffix")`;
3. adds helpers whose name is a fixed literal, and any full `"sensor.x.y"`
   string written elsewhere.

Scanning only for literal ids found 6 of ~22 and silently missed the rest,
including `sensor.camera.normals`.

A sensor is the most user-facing thing CARLA ships and has a dedicated reference
page, so a missing one is high-impact: there is no other place a user would look.

## 6. catalogue

Vehicles, walkers and props are **not** registered in C++. The factories load
JSON catalogues off disk, so the actor inventory is static data:

```cpp
// VehicleActorFactory::GetDefinitions()
LoadVehicleParametersArrayFromFile("VehicleParameters.json", VehiclesParams);
LoadVehicleParametersArrayFromFile(<Map>/Vehicles.json, MineVehiclesParams);
// then content packs, later entries overriding earlier by make.model
```

| catalogue | id built as |
|---|---|
| `VehicleParameters.json` | `vehicle.<Make>.<Model>` |
| `WalkerParameters.json` | `walker.pedestrian.<Id>` |
| `PropParameters.json` | `static.prop.<Name>` |

Ids are lowercased, matching `FillIdAndTags` (`ActorBlueprintFunctionLibrary.cpp:224`).

The audit unions **every** copy of each catalogue — base, per-map
(`Config/<Map>/Vehicles.json`) and content packs — because reading only the base
file under-reports, and an audit that under-reports is worse than none.

A finding distinguishes *"not in catalogue_vehicles.md, only in X"* (misfiled)
from *"absent from all of Docs/"* (missing).

Expect `bp_library.md` to drift here: it is generated from a live server, so it
is a snapshot of whatever build someone last ran it against, while the JSON is
the source of truth.

## 6b. catalogue-stale

The mirror of `catalogue`: a blueprint id a catalogue page names that nothing
knows about. Ids are read off the page, so the pattern has to require a make
and a model -- `vehicle.apply_control(...)` in a code snippet matches a looser
one and produces three false findings on `catalogue_vehicles.md` alone.

This is the one signal that uses a **running server**, through `--host`/`--port`
(default `127.0.0.1:2000`). Without one it compares against the JSON catalogues
and says so in the section; with one it adds the live blueprint library.

**It adds, it does not replace.** The blueprint library is per map: Mine_01's
`vehicle.miningtruck.miningtruck` comes from
`Content/Carla/Config/Mine_01/Vehicles.json` and is not registered while Town10
is loaded. Comparing against the live library alone reports every per-map actor
as deleted. An entry is stale only when neither source has it.

## 7. stale

The mirror of `binding`: a documented class or method with no counterpart in
`PythonAPI/carla/src/*.cpp`. Worse than a missing entry, because a reference
page for something renamed or deleted reads as authoritative.

The C++ side scans `class_<...>("X")`, `.def`, `.add_property`,
`.def_readwrite`, `.def_readonly`, `.add_static_property`, `enum_<...>`, and
`.value`. Dunders Boost supplies itself are exempt.

Both `def_name` and `var_name` are checked. Variables matter most here: three
of the four typos this signal finds (`axel_type`, `intertia_tensor_scale`,
`max_handbrake_torque`) are instance variables, and each is a documented
attribute that raises. `.add_static_property` has to be in the C++ list or
every enum value documented as an instance variable is reported — 35 false
findings from `LandmarkType` alone.

Names are matched across all classes, not per class, so a member documented on
the wrong class is not reported as long as some class exposes that name.

**Regex caution.** Match up to the opening paren, not the first `>`:
declarations like `class_<cc::Actor, boost::noncopyable, std::shared_ptr<cc::Actor>>("Actor"`
contain nested templates, and a `[^>]*` pattern stops inside `shared_ptr<...>`.
That bug silently reported every real class as stale and made `binding`
under-report by two thirds.

## 4. link

Checks every relative markdown link in `Docs/`, both inline `[x](y)` and
reference definitions `[x]: y`. Three failure modes:

- **target page does not exist** — the page was renamed or never existed.
- **anchor not found** — the page exists, the `#fragment` does not. Anchors come
  from explicit `<a name="...">` tags and from heading slugs.
- **missing `.md`** — the link has no extension, so MkDocs leaves it alone and it
  resolves *below* the current page (`/tuto_G_getting_started/python_api`). This
  is the bug class PR #9927 fixed; it renders as a working link and 404s.

Fenced code blocks and HTML comments are stripped before scanning. Links inside
them are examples or deliberately parked, and counting them produced false
positives when these checks were first run by hand.

Links pointing outside `Docs/` (into `PythonAPI/`, `LibCarla/`) are **not**
reported: they resolve on GitHub and 404 on the docs site, which is a deliberate
trade rather than rot.

## 5. orphan

Lists `Docs/*.md` files that no live line of `mkdocs.yml` references. Commented
nav lines do not count as a reference — a parked page is still unreachable.

Expect a large number, and expect most to be intentional: fragments included by
other pages, work in progress, and pages deliberately kept out of the site. The
signal's value is the handful that *should* be reachable and silently are not.
Triage this one last.

## What this audit cannot see

Everything that exists only when the simulator runs:

- `world.get_blueprint_library()` — vehicles, walkers, props and their
  attributes. These are **content**, so a new asset appears in no source diff
  and no changelog entry.
- `client.get_available_maps()` — which maps this build actually cooked.
- recommended values and ranges per blueprint attribute.

`PythonAPI/docs/bp_doc_gen.py` already regenerates `Docs/bp_library.md` from a
live server on `127.0.0.1:2000`. For an audit, run it to a temporary path and
diff against the committed page — a non-empty diff is the finding. Do not let it
overwrite `Docs/bp_library.md` during an audit: the deliverable is a report, not
a mutated working tree.

Run the runtime audit on the **same code and content** as the static one. Asset
availability varies by content branch, so a mismatched pair reports phantom gaps.
