# Autoware on CARLA UE 5.8 — the contract, and what is measured

Everything below was read from `ue58-dev` HEAD `718efd7cc` (engine 5.8.0,
CARLA 0.10.0) or measured against a live 0.10.0 server on this machine. The
**Evidence** column says which.

## 2. The topic contract

Read straight from the constructors, which is what `autoware.sh topics` does.

`AutowareVehicleStatusPublisher` — base `rt/vehicle/status`, QoS
`QosProfile::ReliableVolatile()` (the comment says "per tier4's
AutowarePublisher: RELIABLE / VOLATILE / KEEP_LAST 1"):

```
rt/vehicle/status/velocity_status
rt/vehicle/status/steering_status
rt/vehicle/status/control_mode
rt/vehicle/status/gear_status
rt/vehicle/status/turn_indicators_status
rt/vehicle/status/hazard_lights_status
```

`AutowareControlSubscriber` — base `rt/control/command`, QoS
`QosProfile::ReliableTransientLocal()` ("so the latest latched command survives a
late join"):

```
rt/control/command/control_cmd
rt/control/command/gear_cmd
rt/control/command/turn_indicators_cmd
rt/control/command/hazard_lights_cmd
rt/control/command/emergency_cmd
rt/vehicle/engage
```

Note the asymmetry in durability. Status is volatile because a stale velocity is
worse than none; commands are latched because a simulator that restarts mid-run
must not sit unengaged waiting for the next command.

`AutowareGNSSPublisher` publishes on the **sensor's own** base topic rather than
a fixed name, so its topic follows the `ros_name` / `ros_topic_name` you give
`sensor.other.autoware_gnss`.

The `rt/` prefix is DDS-side; a ROS 2 node sees `/vehicle/status/velocity_status`.

## 3. Two switches, both required

- **Compile time**: `-DENABLE_ROS2=ON`. Cannot be turned on later — there is no
  runtime fallback, and a build without it has no DDS interface at all. `probe`
  reads it from `CMakeCache.txt`, the only honest source
  ([[build-carla-ue58]]).
- **Run time**: `-ros2`, single dash. `--ros2` is silently ignored on ue58.

Verified on this machine: `ENABLE_ROS2:BOOL=ON` in `Build/Release/CMakeCache.txt`.

The two Autoware **blueprints exist regardless** of `-ros2` — they are actor
definitions, not publishers. So `sensors` passing does not prove topics will flow.

## 4. Who owns the simulation

`autoware_demo.py` is the CARLA-side driver and it owns world settings, the ego,
the sensor rig and the ticking. The Autoware side never ticks CARLA. Practical
consequences:

- start the demo **before** the stack, and leave it running;
- synchronous mode is the demo's job (`--run_async` opts out, `--hz_rate` sets
  the rate, `--substepping` enables physics substeps);
- `--resync` re-syncs when lag exceeds a threshold, which matters because a
  first-run VAD engine build stalls the stack side for minutes;
- `--mgrs_off` disables the MGRS offset. Autoware works in MGRS coordinates, so
  the demo applies an offset by default; turning it off is a debugging aid the
  script itself suggests when the map projector disagrees.

It writes its own post-process profile at startup —
`deploy_postprocess_profile("autoware_demo", AUTOWARE_POSTPROCESS_SETTINGS)`
lands `Content/Carla/Config/PostProcess/autoware_demo.json`. That file is
generated, not shipped content: deleting it is harmless, and it is untracked in
the content repository.

## 5. Maps: two different map concepts

CARLA drives from OpenDRIVE (`.xodr`); Autoware needs a Lanelet2 map plus a
point-cloud map plus a projector description:

```
map_tools/maps/<Town>/lanelet2_map.osm
map_tools/maps/<Town>/pointcloud_map.pcd
map_tools/maps/<Town>/map_projector_info.yaml
```

Generated by `map_tools/generate_map_artifacts.py` (which calls
`generate_lanelet2_map.py`, `generate_pointcloud_map.py`,
`write_projector_info.py`), or fetched with `fetch_prebuilt_maps.sh`. Measured
here: `Town10HD` is already complete in this checkout.

`--mode classical` localises by NDT **against the point cloud**, so a missing or
partial `.pcd` shows up as a localisation failure rather than a file error.
`--mode e2e` takes localisation from simulator ground truth, so it tolerates a
weaker map.

## 6. The launcher, and why the dry run matters

`run/run_carla_autoware.sh --mode classical|e2e` does a lot more than start one
process. Its dry run (what `autoware.sh stack` prints by default) shows:

- the exact `ros2 launch` command per mode, with `RMW_IMPLEMENTATION`,
  `CYCLONEDDS_URI` pointing at a generated `logs/dds/cyclonedds.xml`, and
  `ROS_DOMAIN_ID`;
- for `e2e`, that it currently launches `autoware_tensorrt_vad
  vad_carla_tiny.launch.xml` with sensing/localization/perception off, and would
  switch to `autoware_launch e2e_simulator.launch.xml … use_e2e_planning:=true`
  once `autowarefoundation/autoware_launch#1685` is in the workspace;
- the readiness gates it waits on: `/api/operation_mode/change_to_autonomous`
  appearing in `ros2 service list`, then `VAD model and interface initialized
  successfully` in the log (cached engines ≈ 1 min, a first run builds TensorRT
  engines and takes tens of minutes), then up to 12 retries of the
  `change_to_autonomous` service call;
- pid and container bookkeeping in `run/logs/carla_autoware.pids` and
  `.containers`, torn down by `run/stop_all.sh --log-dir …`.

It also sanitises the environment on purpose: `CONDA_*`, `VIRTUAL_ENV`,
`PYTHONPATH`, `PYTHONHOME` are unset and conda/miniforge entries are stripped
from `PATH`, keeping only enough of the original `PATH` to find a Python that can
`import carla`.

**RMW asymmetry**: the simulator side defaults to `fastdds` and the script warns
that `cyclonedds` there has a known fragmented-receive bug; the Autoware side
always uses cyclonedds (or zenoh). This is the one configuration detail most
likely to produce "topics exist but nothing arrives".

## 7. What was NOT verified

- The Autoware stack was never launched here: no source workspace at
  `~/autoware`. A docker image
  (`ghcr.io/autowarefoundation/autoware:universe-cuda-jazzy`) is present, so
  `--stack docker` is plausible on this machine but untried.
- No live topic capture. The contract above is from the constructors, not from
  `ros2 topic list`. The `ros2` group's [[visualize-ros-rviz]] is the tool for
  closing that gap.
- The ROS-2-enabled server did not reach a listening port inside a 120 s wait in
  this session (a plain server did, in ~20 s). Slower start, not a failure — but
  it means the end-to-end path is unmeasured.
- ROS 2 Humble is what the launcher sources (`/opt/ros/humble/setup.bash`), while
  the local docker image is a `jazzy` build. Whether that combination works was
  not tested.
